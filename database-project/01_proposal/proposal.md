# 1차 기획안 — BalanceBook

> 2026-2 데이터베이스 프로젝트 1차 기획안  
> 작성일: 2026.10.10. · DBMS: PostgreSQL

---

## 1. 프로젝트명

BalanceBook (밸런스북) — 소규모 사업자용 복식부기 회계 관리 서비스 (간이 ERP 회계 모듈)

- 이름의 의미: 차변과 대변이 항상 균형(balance)을 이루고, 계정마다 잔액(balance)을 바로 확인할 수 있는 장부(book)
- 복식부기에서 거래의 차변과 대변 합계가 같아야 한다는 균형 규칙을 사람이 일일이 확인하며 입력하는 대신, **데이터베이스의 제약조건과 트랜잭션으로 지킬 수 있도록 하는 것**이 이 프로젝트의 핵심이다.

---

## 2. 프로젝트 주제 및 비즈니스 모델

### 2-1. 주제와 목적

| 항목 | 내용 |
| --- | --- |
| 주제 | 소규모 사업자의 거래를 복식부기 전표로 기록·조회·집계하는 간이 ERP의 회계 모듈 |
| 목적 | 차변·대변이 맞지 않는 전표는 저장 단계에서 막고, 시산표·손익계산서는 전표 데이터에서 SQL로 바로 산출한다 |
| 데이터베이스 / 스키마 | `balancebook` / `acct` |
| 예시 사업자 | 가상의 카페 |

**주제 선정 이유**

- 회계를 공부하며 익힌 장부의 업무 규칙(차대 일치, 월 마감, 마감 후 정정 시의 역분개)을 바탕으로, 이 규칙을 DB의 제약조건·트랜잭션으로 직접 구현해 보고 싶었다.
- 회계 데이터는 전표·계정과목·거래처·마감 기간이 서로 연결되어 있다. PK/FK, N:M, 정규화, JOIN, 집계, 트랜잭션의 적용이 필수적이다.


### 2-2. 비즈니스 모델

| 항목 | 내용 |
| --- | --- |
| 고객 | 개인사업자, 소규모 법인 (카페, 학원, 소규모 쇼핑몰 등) |
| 가치 | 입력 오류를 저장 단계에서 차단, 장부와 보고서를 한 곳에서 산출, 수정 이력 보존 |
| 차별점 | 엑셀 장부는 입력 오류를 막지 못하고, 전문 회계 프로그램은 소규모 사업자가 쓰기에 지식적·경제적 부담이 크다. 필수 장부 기능을 제공하고, 입력 오류는 제약조건과 트랜잭션으로 막는다. |
| 이용 방식 | 로그인 → 사업자 선택 → 전표 입력·조회, 보고서 확인. 세무대리인은 한 계정으로 여러 사업자를 오가며 관리 |
| 수익 구조(가정) | 사업자 1곳당 월 구독료. 세무대리인이 여러 사업자를 맡으면 사업자 수만큼 과금 |

## 3. 해결하고자 하는 문제

소규모 사업자는 거래를 엑셀이나 수기 장부로 관리하는 경우가 많다. 이때 생기는 문제와 DB로 해결하는 방법은 다음과 같다. '관련 테이블'은 6절의 테이블이 각각 어떤 문제에서 나왔는지 보여 준다.

| 문제 | 엑셀 장부에서 생기는 일 | DB로 해결하는 방법 | 관련 테이블 |
| --- | --- | --- | --- |
| 차변·대변 불일치 | 한쪽만 입력하거나 금액을 잘못 써도 그대로 저장된다 | 전표와 분개를 한 트랜잭션으로 저장하고, 합계가 다르면 ROLLBACK | `journal_entries`, `journal_lines` |
| 기준 정보 오류 | 계정과목·거래처 이름을 행마다 글자로 적어 `외상매출금` / `외상 매출금`처럼 갈리고, 이름을 바꾸면 과거 행을 모두 고쳐야 한다 | 계정과목·거래처는 별도 테이블에 한 번만 저장하고 분개는 FK로만 참조. 오타가 생길 수 없고, 이름 변경은 한 곳만 고친다 | `accounts`, `account_types`, `partners` |
| 보고서 불일치 | 장부를 고치면 시산표·손익계산서를 다시 만들어야 한다 | 보고서를 따로 저장하지 않고 전표에서 집계 SQL로 매번 산출 | `journal_lines`, `accounts` |
| 마감 후 임의 수정 | 이미 확정해 보고한 달의 숫자를 누군가 고치면 그대로 바뀐다 | 마감된 달의 전표는 수정·삭제를 막고, 정정은 열려 있는 달의 역분개 전표로만 할 수 있도록 한다 | `fiscal_periods`, `journal_entries` |
| 수정 이력 없음 | 어느 거래를 누가 언제 고쳤는지 추적하기 어렵다 | 전표를 바꿀 때마다 변경 기록 테이블에 남긴다 | `entry_change_logs`, `users` |
| 사업자별 자료 분산 | 세무대리인이 사업자마다 엑셀 파일을 따로 받아 관리해 파일이 흩어지고 최신본이 헷갈린다 | 모든 사업자의 장부를 한 DB에 두고, 사용자–사업자 N:M 연결 테이블로 맡은 사업자에만 접근 | `companies`, `users`, `company_users` |
| 증빙 분리 보관 | 영수증·세금계산서가 장부와 따로 보관돼 어느 거래의 증빙인지 찾기 어렵다 | 증빙 정보를 전표에 FK로 연결 | `evidences` |

## 4. 주요 사용자

| 사용자 | 하는 일 | 주로 다루는 데이터 |
| --- | --- | --- |
| 대표 | 손익계산서·월별 추이 등 보고서 조회, 담당자·세무대리인을 자기 사업자에 연결 | 보고서 조회(SELECT), `company_users` 추가 |
| 회계 담당자 | 거래처 관리, 전표 입력·수정, 증빙 등록 | `partners`, `journal_entries`, `journal_lines`, `evidences` 추가·수정 |
| 검토자(세무대리인 등) | 여러 사업자의 전표 검토, 월 마감 처리 | 전표 조회, `fiscal_periods` 마감 처리 |
| 서비스 운영자 | 모든 사업자가 함께 쓰는 표준 계정 관리 | `accounts`, `account_types` 추가·수정 |

한 사람이 여러 사업자를 맡을 수 있고, 같은 사람이라도 사업자마다 역할이 다를 수 있다.  
→ 사용자와 사업자는 **N:M 관계**이고, 역할은 사업자마다 달라질 수 있어 둘을 잇는 연결 표에 둔다.

## 5. 핵심 기능

| 구분 | 기능 | 주로 쓰는 DB 개념 |
| --- | --- | --- |
| 기준 정보 관리 | 계정과목(상위·하위 계층, 예: 유동자산 > 현금)·거래처 등록/조회/수정/삭제. 계정과목은 서비스 운영자, 거래처는 회계 담당자가 관리 | CRUD, FK (사용 중인 계정·거래처는 삭제 불가) |
| 사용자 연결 | 대표가 담당자·세무대리인을 자기 사업자에 연결하고 역할 지정 | N:M 연결 테이블에 INSERT |
| 전표 입력 | 전표 한 장에 분개 여러 줄 입력, 차변 합계 = 대변 합계일 때만 저장 | 트랜잭션, CHECK |
| 전표 검색 | 기간·계정·거래처·적요 키워드로 필터, 일자순·금액순 정렬 | WHERE, ORDER BY, 인덱스 |
| 계정별 원장 | 특정 계정의 거래 내역과 기간 잔액 | JOIN, 집계 |
| 거래처별 잔액 | 외상매출금·외상매입금을 거래처별로 집계 | GROUP BY |
| 보고서 | 시산표, 손익계산서, 월별 매출·비용 추이 | GROUP BY, 서브쿼리, SELF JOIN |
| 월 마감 | 마감된 달의 전표 수정·삭제 차단, 정정은 역분개 | 무결성 규칙, 트랜잭션 |
| 증빙 관리 | 전표에 세금계산서·카드영수증 등 증빙 연결, 증빙이 없는 전표 찾기 | 1:N, LEFT JOIN (OUTER JOIN) |
| 변경 이력 조회 | 전표별로 누가 언제 무엇을 바꿨는지 조회 | 1:N, JOIN |

## 6. 예상 테이블 구성 및 데이터 구조

**굵게** = PK, *기울임* = FK

| # | 테이블 | 한 행의 의미 | 주요 컬럼 | 필요한 이유 |
| --- | --- | --- | --- | --- |
| 1 | `companies` | 서비스를 쓰는 사업자 한 곳 | **company_id**, name(상호), business_no(사업자등록번호) | 모든 장부 데이터의 주인. 여러 사업자의 데이터를 구분 |
| 2 | `users` | 로그인 사용자 한 명 | **user_id**, email(로그인용), name | 전표 작성자·마감 처리자·변경자 기록 |
| 3 | `company_users` | 사용자 한 명이 사업자 한 곳에서 맡은 역할 | **company_user_id**, *company_id*, *user_id*, role(역할) | 사용자와 사업자는 N:M 관계라서 둘을 이어 주는 표가 필요하다. 역할은 사업자마다 달라질 수 있어 이 표에 둔다 |
| 4 | `account_types` | 계정 분류 하나 (자산·부채·자본·수익·비용) | **type_code**, name, normal_side, statement | 자산이면 차변, 부채면 대변처럼 분류가 정하는 정보는 이 표에 한 번만 적고, 계정은 분류만 가리킨다 |
| 5 | `accounts` | 계정과목 하나 (예: 현금, 외상매출금) | **account_id**, code(계정코드), name, *type_code*(분류), *parent_account_id*(상위 계정) | 계정 이름을 이 표에 한 번만 적고 분개는 번호로만 가리킨다. 그래서 오타가 생기지 않고, 이름을 바꿀 때도 한 곳만 고치면 된다. 상위 계정 칸으로 '유동자산 > 현금' 같은 계층을 표현한다 |
| 6 | `partners` | 사업자의 거래처 하나 | **partner_id**, *company_id*, name(거래처명), business_no(사업자등록번호) | 외상 거래를 거래처별로 관리한다. 거래처 이름도 이 표에 한 번만 적고 분개는 번호로 가리킨다 |
| 7 | `fiscal_periods` | 사업자의 월별 마감 기간 하나 (예: 2026년 10월) | **period_id**, *company_id*, year_month(연월), is_closed(마감 여부), *closed_by*(마감한 사람) | 달마다 마감 여부를 기록하고, 마감된 달의 전표를 고치지 못하게 막는 기준이 된다 |
| 8 | `journal_entries` | 전표 한 장 (거래 1건) | **entry_id**, *company_id*, entry_date(전표일자), description(적요), *created_by*(작성자), *reversal_of_entry_id*(역분개로 취소하는 원래 전표) | 날짜·적요처럼 전표 한 장에 한 번만 있는 정보를 담는다. 역분개 전표는 어떤 전표를 취소하는지 같은 표의 전표 번호로 가리킨다 |
| 9 | `journal_lines` | 전표 안의 분개 한 줄 | **line_id**, *entry_id*, *account_id*, *partner_id*(거래처, 없을 수도 있음), debit_amount(차변 금액), credit_amount(대변 금액) | 전표와 계정과목은 N:M 관계라서 둘을 이어 주는 표가 필요하다. 전표마다 분개 줄 수가 달라 따로 둔다 |
| 10 | `evidences` | 전표에 연결한 증빙 하나 | **evidence_id**, *entry_id*, evidence_type(증빙 종류), issue_date(발행일), amount(증빙 금액) | 전표 한 장에 증빙이 여러 개일 수 있어 따로 둔다. 증빙 금액과 전표 금액을 비교해 입력 실수를 찾을 수 있다 |
| 11 | `entry_change_logs` | 전표 변경 기록 한 건 | **log_id**, *entry_id*, *user_id*(변경한 사람), action(생성·수정·역분개), changed_at(변경 시각) | 전표 한 장에 기록이 여러 개 쌓여야 해서 따로 둔다. 전표에 칸으로 두면 마지막 기록만 남는다 |

### 6-1. 테이블 관계

| 관계 | 종류 | 이유 |
| --- | --- | --- |
| companies – partners / fiscal_periods / journal_entries | 1:N | 사업자 한 곳이 거래처·마감 기간·전표를 여러 개 가진다 |
| users – companies | N:M (연결 표: `company_users`) | 세무대리인 한 명이 여러 사업자를 맡고, 사업자 한 곳에도 사용자가 여러 명이다 |
| users – journal_entries / fiscal_periods / entry_change_logs | 1:N | 사용자 한 명이 전표 여러 장을 작성하고, 여러 달을 마감하고, 변경 기록을 여러 건 남긴다 |
| account_types – accounts | 1:N | 분류 하나에 계정이 여러 개 |
| accounts – accounts | 1:N (같은 표 안) | 상위 계정 하나 아래에 하위 계정이 여러 개 (예: 유동자산 > 현금, 외상매출금) |
| journal_entries – accounts | N:M (연결 표: `journal_lines`) | 전표 한 장에 계정이 여러 개 쓰이고, 계정 하나도 여러 전표에 쓰인다 |
| partners – journal_lines | 1:N | 거래처 하나가 여러 분개에 나온다. 거래처가 없는 분개도 있다. |
| journal_entries – evidences / entry_change_logs | 1:N | 전표 한 장에 증빙·변경 기록이 여러 개 |
| journal_entries – journal_entries | 1:1 (같은 표 안, 선택) | 역분개 전표 하나가 원래 전표 하나를 취소한다. 역분개가 없을 수도 있다 |


```text
users            1 ── N  company_users  N ── 1  companies
journal_entries  1 ── N  journal_lines  N ── 1  accounts
```


### 6-2. 데이터 예시

**계정 분류 (`account_types`)**

| type_code | name | normal_side | statement |
| --- | --- | --- | --- |
| ASSET | 자산 | 차변 | 재무상태표 |
| LIABILITY | 부채 | 대변 | 재무상태표 |
| EQUITY | 자본 | 대변 | 재무상태표 |
| REVENUE | 수익 | 대변 | 손익계산서 |
| EXPENSE | 비용 | 차변 | 손익계산서 |


**전표 한 장 = `journal_entries` 1행 + `journal_lines` 여러 행**

예: 2026-10-02 원두 외상 매입 (세금계산서 330,000)

`journal_entries`

| entry_id | entry_date | description |
| --- | --- | --- |
| 1 | 2026-10-02 | 원두 외상 매입 |

`journal_lines`

| line_id | entry_id | 계정과목 | 거래처 | 차변 | 대변 |
| --- | --- | --- | --- | ---: | ---: |
| 1 | 1 | 원재료 | | 300,000 | 0 |
| 2 | 1 | 부가세대급금 | | 30,000 | 0 |
| 3 | 1 | 외상매입금 | 가나로스터리 | 0 | 330,000 |
| | | **합계** | | **330,000** | **330,000** |

- 세 줄 모두 entry_id가 1이라서 같은 전표의 분개다.
- 전표마다 분개 줄 수가 다르다(2줄, 3줄, 그 이상). 그래서 분개를 전표 테이블의 칸으로 늘어놓지 않고 별도 테이블로 분리한다.
- 차변 합계 330,000 = 대변 합계 330,000일 때만 저장된다.
- 실제 `journal_lines`에는 계정과목·거래처 이름 대신 번호(account_id, partner_id)가 저장되고, 화면에서는 JOIN으로 이름을 붙여 보여 준다.

### 6-3. 업무 규칙 초안

| 업무 규칙 | 방법 |
| --- | --- |
| 분개 한 줄은 차변 또는 대변 중 한쪽에만 금액이 있다 | `CHECK ((debit_amount > 0 AND credit_amount = 0) OR (debit_amount = 0 AND credit_amount > 0))` |
| 전표 한 장의 차변 합계 = 대변 합계 | 여러 행에 걸친 규칙이라 CHECK로는 검사할 수 없다 → 전표와 분개를 **한 트랜잭션**으로 저장하고, 합계가 다르면 ROLLBACK |
| 금액에 소수 오차가 있으면 안 된다 | 금액 칸은 `NUMERIC` 타입 사용 (`FLOAT` 사용 안 함) |
| 사업자등록번호·계정코드·이메일은 중복될 수 없다 | `UNIQUE` |
| 같은 사업자의 같은 달 마감 기간은 하나뿐이다 | `UNIQUE (company_id, year_month)` |
| 같은 사람을 같은 사업자에 두 번 연결할 수 없다 | `UNIQUE (company_id, user_id)` |
| 거래에 쓰인 계정과목·거래처는 삭제할 수 없다 | FK로 삭제를 거부 (`ON DELETE RESTRICT`) |
| 마감된 달의 전표는 수정·삭제할 수 없다 | 저장 전에 그 달의 마감 여부를 확인 |
| 마감된 전표의 오류는 열려 있는 달에 정정한다 | 역분개 전표로 원래 전표를 취소한 뒤 올바른 전표를 다시 입력한다. 역분개 전표의 `reversal_of_entry_id` 칸에 원래 전표 번호를 적는다 |


### 6-4. 아직 정하지 않은 것

- 계정과목을 모든 사업자가 함께 쓸지, 사업자마다 따로 둘지. 1차에서는 모든 사업자가 같은 표준 계정과목표를 쓴다고 가정한다. 소규모 사업자라 충분할 것으로 예상된다.
- 대손충당금·감가상각누계액처럼 자산으로 분류되지만 잔액이 대변에 남는 계정이 있다. 차변/대변 방향을 분류 표에만 둘지, 계정마다 예외를 둘 수 있게 할지 정한다. 방향 칸이 필요할 수 있겠지만, 이번 범위에서는 거의 쓰이지 않아 추후에 정할 것이다.
- 전표에 마감 기간 번호를 적어 둘지, 전표일자로 해당 달을 찾을지. 번호를 적어 두면 조회는 편하지만 날짜와 기간이 서로 어긋날 위험이 있다. 전표일자로 찾는 것이 좋아보이기는 한다.
- 분개 금액을 차변 금액·대변 금액 두 칸으로 둘지, 방향(차/대) 칸과 금액 칸으로 둘지. 장부 모양으로 하는 것이 쉬워보이므로 두 칸을 두는 것이 맞아 보인다.
- 마감 전 전표는 삭제를 허용할지, 항상 역분개로만 정정할지. 삭제보다는 기록을 남기는 편이 좋아 보인다.
- 서비스 운영자를 사용자 표에서 어떻게 구분할지 고민이지만, 운영자 칸을 새로 넣으면 될 것 같다.

## 7. 향후 구현 계획

PostgreSQL로 데이터베이스를 만들고, Python(Streamlit)으로 DB와 연결된 웹 화면을 만든다.

### 7-1. 데이터베이스 활용 계획

| 수업 개념 | 적용할 곳 |
| --- | --- |
| ERD, 1:N / N:M | 6-1의 관계. N:M 두 곳은 연결 표(`company_users`, `journal_lines`)를 두어 1:N 두 개로 나눈다. ERD는 2차에서 작성한다 |
| PK / FK | 모든 표는 자기 번호를 PK로 둔다. 다른 표를 가리키는 칸은 FK로 둔다 |
| 정규화 | 같은 정보는 한 번만 적도록 표를 나눈다. 계정 분류 표를 따로 두고, 분개는 계정·거래처를 번호로만 가리킨다 |
| 데이터 타입 | 금액 `NUMERIC`, 전표일자 `DATE`, 변경 시각 `TIMESTAMPTZ` |
| 무결성 제약 | CHECK(분개 한 줄은 한쪽에만 금액), UNIQUE(사업자등록번호·계정코드·이메일 등), NOT NULL, FK(거래에 쓰인 계정·거래처 삭제 거부) |
| JOIN | 전표 조회(전표 + 분개 + 계정 + 거래처), 증빙 없는 전표 찾기(LEFT JOIN), 계정 계층(SELF JOIN) |
| GROUP BY / 집계 | 시산표, 손익계산서, 거래처별 잔액, 월별 추이 |
| 서브쿼리 | 평균보다 금액이 큰 거래 찾기, 마감되지 않은 달의 전표 찾기 |
| 인덱스 | 자주 쓰는 조회를 빠르게 한다. 사업자·기간으로 전표 찾기는 `journal_entries (company_id, entry_date)`, 계정별 원장은 `journal_lines (account_id)`에 인덱스를 만든다 |
| 트랜잭션 | 전표 저장(전표 + 분개 + 변경 기록을 한 묶음으로 하고, 차변·대변 합계가 다르면 ROLLBACK), 월 마감 처리 |

### 7-2. 최종 시연 목표

1. 가상 카페의 한 달 거래(원두 외상 매입, 카드 매출, 임차료 지급 등)를 전표로 입력한다.
2. 차변·대변 합계가 다른 전표를 저장하면 거부되는 장면을 보여 준다.
3. 입력한 전표가 시산표·손익계산서에 바로 반영되는 장면을 보여 준다.
4. 월 마감 후 수정을 시도하면 거부되고, 역분개로 정정하는 장면을 보여 준다.
5. 거래에 쓰인 거래처를 삭제하려 하면 거부되는 장면을 보여 준다.
